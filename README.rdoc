== README

= Schengen Calculator

Caclulator to help track the 90/180 day schengen visa rule for travellers in Europe. 
I had created similar functionality in Excel spreadsheet for my personal use when i was travelling in Europe, and thought it would be helpful for others to put online.

Live site can be found here: http://www.schengen-calculator.com


== System Dependencies
* Database: PostgreSQL : https://wiki.postgresql.org/wiki/Detailed_installation_guides
* Ruby version 3.3.12 (see src/.ruby-version and src/Gemfile)
* Rails version 7.2.4 (see src/Gemfile.lock)
* Docker Desktop or Docker Engine with Docker Compose, for local PostgreSQL


== Application setup
Start Docker Desktop (or your Docker daemon). Install Ruby 3.3.12 using RVM or your preferred Ruby version manager, and configure <tt>src/config/secrets.yml</tt> as described below.

From the repository root, run:

  cd src
  rvm use 3.3.12
  bundle install
  docker compose up -d postgres
  bundle exec rails db:prepare
  bundle exec rails server

If using RVM for the first time, run <tt>rvm install 3.3.12</tt> before <tt>rvm use</tt>. With another version manager, select the version in <tt>src/.ruby-version</tt> instead.

Open http://localhost:3000/en/about to view the information page, or http://localhost:3000/en/visits for Trips. Stop the Rails server with Ctrl+C.

=== Database setup and migrations

<tt>db:prepare</tt> initializes and seeds a new database, or runs pending migrations on an existing initialized database. With the default local configuration, these commands target the development database, not production.

After pulling changes, you can explicitly apply pending migrations from <tt>src</tt>:

  bundle exec rails db:migrate

Do not run <tt>db:seed</tt> as a routine update: this project's seed script deletes existing people, users, countries and continents before loading reference and sample data. Reserve it for a fresh/disposable local database. Use <tt>bundle exec rails db:update_countries</tt> to refresh country reference data without reseeding accounts.

=== Stale styles or JavaScript locally

If local precompiled assets hide recent changes, stop the server and run from <tt>src</tt>:

  bundle exec rails assets:clobber
  bundle exec rails server

This removes generated assets, not source files. Reload the browser afterward; development serves the current source assets.


== Configuration Management

The application uses a custom AppConfig wrapper to manage secrets and environment variables consistently across all environments.

=== Development & Test Environments

Secrets are stored in <tt>config/secrets.yml</tt> (not committed to production). This file is automatically loaded into ENV variables at boot time.

Example secrets.yml structure:
  development:
    secret_key_base: your-dev-key
    facebook_id: 'your-dev-id'
    facebook_secret: 'your-dev-secret'
    facebook_callback_url: 'http://localhost:3000/users/auth/facebook/callback'
    aws_access_key_id: 'your-dev-key'
    aws_secret_key: 'your-dev-secret'
    brevo_login: 'your-dev-email'
    brevo_password: 'your-dev-password'

=== Production Environment

Production secrets are stored in AWS Systems Manager Parameter Store. Lambda environment configuration contains their parameter names; Rails retrieves boot-time secrets when a container starts and loads other runtime secrets on demand (see Deployment section below).

=== Accessing Configuration

All configuration is accessed via the <tt>AppConfig</tt> class:
  AppConfig.facebook_id
  AppConfig.facebook_secret
  AppConfig.secret_key_base

This provides:
* Type safety - misspell a method and get an error
* Single source of truth - all config keys defined in lib/app_config.rb
* Consistent API across development and production
* No deprecated Rails.application.secrets usage


== Country Data Management

*Source of Truth:* db/data/countries.xml

The countries.xml file is the authoritative source for all country-related data in the application, including:
* Country codes (ISO 2-letter and 3-letter)
* Country names (English)
* Schengen Area membership status
* Schengen start dates (when countries joined the Schengen Area)
* Visa requirement information

To update country data in the database after modifying countries.xml:
* Locally: run command <tt>bundle exec rails db:update_countries</tt> from <tt>src</tt>
* Deployments: Automatically runs through the private Ops Lambda (see Deployment section)

Note: Direct database modifications to country data will be overwritten on the next deployment or when the update_countries task runs.


= After updating seed countries data
* Run <tt>bundle exec rails db:update_countries</tt> from <tt>src</tt>

= To clean up guest user accounts older than 30 days
* run command <tt>`./bin/rake db:guest_cleanup`</tt>
* Optionally pass in a "to date" to delete guest accounts last modified up to that date
* run command <tt>`./bin/rake db:guest_cleanup["2010-10-01"]`</tt>


== Translation Management (i18n)

The application supports 9 languages: English (en), German (de), Spanish (es), French (fr), Hindi (hi), Turkish (tr), Chinese Simplified (zh-CN), Portuguese Brazilian (pt-BR), and Arabic (ar).

Translation validation is powered by the i18n-tasks gem (https://github.com/glebm/i18n-tasks), which provides intelligent scanning and validation of translation keys.

=== Available Commands

==== Check Translation Status
Scans all locale files for missing, unused, and placeholder translations:
  rails i18n:check

Output shows:
* Missing translations (keys in English but not in other languages)
* Unused translations (keys in YAML but not used in code)
* Placeholder translations (keys marked with [TRANSLATE] needing human translation)

==== Add Placeholder Translations
Auto-generates placeholder translations for missing keys using [TRANSLATE] prefix:
  rails i18n:add_placeholders

This creates entries like:
  calendar_view_title: "[TRANSLATE] Schengen Calendar View"

Translators should search for [TRANSLATE] and replace with proper translations:
  grep -rn "\[TRANSLATE\]" config/locales/

==== Remove Unused Translations
Removes translation keys that are no longer used in the codebase:
  rails i18n:remove_unused

Warning: Reviews and prompts for confirmation before deletion.

==== Normalize YAML Files
Sorts and formats all locale YAML files for consistency:
  rails i18n:normalize

==== Install Pre-commit Hook
Installs a git hook that automatically validates translations before each commit:
  rails i18n:install_hook

The hook blocks commits if any translation issues are found. Bypass with:
  git commit --no-verify

=== Translation Files
All translations are stored in src/config/locales/:
* Main files: en.yml, de.yml, es.yml, fr.yml, hi.yml, tr.yml, zh-CN.yml, pt-BR.yml, ar.yml
* Namespaced files: days.*.yml, visits.*.yml, blog.*.yml, about.*.yml, countries.*.yml, devise.*.yml, user.*.yml, visas.*.yml

Configuration: src/config/i18n-tasks.yml

=== Workflow for Adding New Translations
1. Add English translation to appropriate config/locales/*.en.yml file
2. Run rails i18n:add_placeholders to generate stubs in other languages
3. Search for [TRANSLATE] and replace with actual translations
4. Commit changes (pre-commit hook will validate)

=== Handling Undetectable Translation Keys

Some translation keys cannot be automatically detected by i18n-tasks because they're used in non-standard ways:

Current whitelisted keys (as of last cleanup):
* days.max_remaining_days - Used as model attribute name
* days.year_summary - Used as controller variable name
* visits.about_page_link - Used as interpolation parameter name

This prevents false "unused key" warnings while documenting why the key is special.

== Facebook OAuth Configuration

The application uses Facebook Login (OAuth) for user authentication.

=== Current Configuration
* Facebook Graph API Version: v26.0
* Required Scopes: email, public_profile
* OAuth Provider: omniauth-facebook gem

=== Android Chrome app-handoff workaround

Set <tt>FACEBOOK_WEB_LOGIN_WORKAROUND=true</tt> at application startup to add
<tt>sdk=joey</tt> to Facebook's authorization request. CDK enables this for both
staging and production via <tt>facebookWebLoginWorkaround: true</tt>, following
successful staging verification. Other stacks default to off unless explicitly enabled.
Disable the CDK flag and redeploy to roll back. Local processes need a restart
after changing the environment variable.

This is an undocumented Facebook web-SDK hint, not a guaranteed public API.
On the tested Pixel 6 with Facebook app links enabled, the original flow aborted;
the hint kept login in Chrome and completed the callback to the visits page.
Keep the POST/CSRF-protected request, OAuth state, code exchange and callback unchanged.
Report: https://www.linkedin.com/pulse/facebook-authentication-saga-why-generalism-back-age-ai-jukka-rohila-llsbe

Run OAuth regression tests with the flag both enabled and disabled. After deployment,
retest Android Chrome with Facebook installed and app links enabled, including a
browser without an existing Facebook session, plus desktop login. Do not use a
successful already-authenticated browser alone to conclude the handoff is fixed.

=== Environment Variables / Parameter Store

The application uses AWS Systems Manager Parameter Store for production secrets. The following parameters must be configured:

* <tt>{paramPath}facebook_id</tt> - Your Facebook App ID
* <tt>{paramPath}secrets/facebook_secret</tt> - Your Facebook App Secret. Store this as an SSM SecureString.
* <tt>{paramPath}facebook_callback_url</tt> - Production OAuth callback URL
* <tt>{paramPath}secrets/secret_key_base</tt> - Rails secret key base (generate with: <tt>rails secret</tt>). Store this as an SSM SecureString.
* <tt>{paramPath}secrets/rails_master_key</tt> - Rails credentials master key. Store this as an SSM SecureString.
* <tt>{paramPath}secrets/db_pooler_url</tt> - Pooled Neon PostgreSQL connection string used by the Rails HTTP Lambda. Store this as an SSM SecureString.
* <tt>{paramPath}secrets/db_direct_url</tt> - Direct Neon PostgreSQL connection string used by the Ops Lambda for migrations, country updates, and guest cleanup. Store this as an SSM SecureString.
* <tt>{paramPath}brevo_login</tt> - Brevo SMTP username
* <tt>{paramPath}secrets/brevo_password</tt> - Brevo SMTP password. Store this as an SSM SecureString.
* <tt>{paramPath}secrets/ga_api_secret</tt> - Google Analytics 4 Measurement Protocol API secret. Store this as an SSM SecureString.
* <tt>{paramPath}cloudfront_origin_auth_header</tt> - Shared CloudFront-to-Lambda origin authentication header. Store this as a high-entropy SSM String; CloudFront origin custom headers do not support CloudFormation <tt>ssm-secure</tt> dynamic references.
* <tt>{paramPath}secrets/schengen_agent_auth_header</tt> - Shared MCP-to-Rails agent authentication header. Store this as an SSM SecureString.

* <tt>/scheng/prod/secrets/schengen_agent_auth_header</tt>

CDK maps ordinary parameters to runtime environment variables such as <tt>FACEBOOK_ID</tt>. Runtime secret values are not injected directly into Lambda environment variables: CDK supplies only their SSM parameter names. At cold start, Rails retrieves the database URL, Rails keys, Facebook secret, and Brevo password in one decrypted <tt>GetParameters</tt> request before Active Record and application initializers run. The HTTP Lambda receives the pooled database parameter name and the Ops Lambda receives the direct parameter name. Rails/MCP resolve the remaining runtime parameters when required. CloudFormation resolves <tt>{paramPath}cloudfront_origin_auth_header</tt> directly into the CloudFront origin custom header so API Gateway/Lambda can identify trusted CloudFront requests.

The legacy top-level SecureString paths and plaintext <tt>{paramPath}db_url</tt>, <tt>rails_master_key</tt>, <tt>secret_key_base</tt>, <tt>facebook_secret</tt>, <tt>brevo_password</tt>, and <tt>task_password</tt> parameters may remain during rollout for rollback. Remove them only after both staging and production have been deployed and verified.

For development and test environments, these values are stored in <tt>config/secrets.yml</tt> and automatically loaded into ENV variables (see Configuration Management section).

== Deployment
* Automatic deployment to AWS Lambda / CloudFront via CDK and GitHub Actions
* CDK application code lives in the /deployment directory

To provision a new environment:
* Create the required SSM parameters referenced in deployment/lib/http-api.ts (the SecureString parameters under secrets/, Facebook configuration, Brevo login, the CloudFront origin header, etc.)
* Bootstrap CDK in the target account/region (`cdk bootstrap aws://ACCOUNT/eu-central-1`)
* Configure GitHub Actions OIDC access to the AWS deployment role.
* Create the GitHub Actions repository variable <tt>AWS_DEFAULT_REGION</tt> (currently <tt>eu-central-1</tt>).

=== GitHub Actions workflow

Two workflows drive deployments:
* Deploy-Staging (same-repository pull requests and pushes to master) → deploys the shared `RailsLambdaStack` staging stack. Staging deployments are serialized so each smoke test checks the version its workflow deployed.
* Deploy-Prod (manual dispatch) → deploys the `SchengTrackProd` stack

Each workflow performs the following steps in the `deploy` job:
1. `cdk deploy` for the appropriate stack
2. Resolve the `OpsLambdaFunctionName` CloudFormation output
3. Invoke the Ops Lambda to run:
   * `db:migrate`
   * `db:update_countries`

Guest cleanup runs separately through the scheduled or manually dispatched GitHub Actions workflow, which invokes the Ops Lambda directly.

After application and database tasks succeed, the `cacheInvalidate` job updates `/schengen/deployment-timestamp`, issues a CloudFront invalidation, runs focused checks against the deployed site, and pre-warms key URLs. A failed smoke check or cache warm-up fails the deployment workflow.

=== Manual task execution

Invoke administrative database tasks through the Ops Lambda using <tt>deployment/scripts/invoke_ops_lambda.sh</tt> and the stack's <tt>OpsLambdaFunctionName</tt> output.
